# 预约并发控制 · 三层防重笔记

> 对应代码：`BookingService.create` / `common/RedisLock` / `SeatMapper.lockForUpdate` / `BookingMapper.findFirstConflict`
>
> 总结一句：**三层不是三个并列的保险，而是一段接力。L1 挡流量，L2 保互斥，L3 定语义。**

---

## 0. 问题的本质

预约 = 「检查某时段没人占」+「插入一条记录」。

问题出在**检查和插入之间有一段时间差**，这叫 check-then-act 竞态：

```
请求 A: 查冲突 → 无占用
请求 B: 查冲突 → 无占用      ← B 在 A 写入之前读的
请求 A: INSERT
请求 B: INSERT                ← 两条都进去了
```

`version` 乐观锁救不了，因为乐观锁防的是「更新同一行」，而这里冲突的是「插入新行」，没有行可以带版本号。

---

## 1. L1：Redis 分布式锁（性能层）

### 1.1 命令与语义

```
SET lock:seat:{seatId}:{date} "<uuid>" NX PX 10000
```

| 片段 | 含义 |
|---|---|
| `SET` | 设值 |
| `key` | 锁名，粒度 = 座位 + 日期 |
| `value` | 令牌（UUID），标明"这把锁是我的" |
| `NX` | Not eXists，只有 key 不存在时才写 |
| `PX 10000` | 10000 毫秒后自动删除 |

成功返回 `OK`，失败返回 `nil`。

### 1.2 为什么要"原子"

**原子 = 一个操作对外表现为"要么全做完，要么完全没做"，中间状态不可见、也插不进别的命令。**

`SET key value NX PX ttl` 一条命令里做了三件事（判存在、写值、设过期），Redis 单线程执行，**中间没有缝**。

对比三条演进路线：

| 写法 | 原子 | 问题 |
|---|---|---|
| `GET` 判断 + `SET` 写入 | 否 | 两个请求同时判断为空，都写成功 |
| `SETNX` + `EXPIRE` | 否（组合） | 中间崩溃 → 锁永不过期 → 死锁 |
| `SET k v NX PX ttl` | 是 | 无 |

**判据：它在 Redis 眼里算"一个"操作，还是"两个"。一个操作内部无缝；两个操作之间就有缝。**

> 补充：Redis 6 之后网络 IO 多线程，但**命令执行仍是单线程**，所以单条命令天然原子。

### 1.3 释放锁为什么必须用 Lua

如果直接 `DEL`：A 的锁因 GC 停顿/慢 SQL 过期 → B 抢到锁 → A 执行 `DEL` 把 B 的锁删了 → B 以为自己还持锁，实际已经裸奔。

所以 value 存随机令牌，删之前比对：

```lua
if redis.call('get', KEYS[1]) == ARGV[1] then
    return redis.call('del', KEYS[1])
else
    return 0
end
```

GET 和 DEL 必须打包成一次原子执行 —— 否则两个动作之间锁可能又过期换人了。

`DEL` 的返回值不能用来判断：删谁的锁都返回 1。

### 1.4 参数为什么这么定

| 参数 | 取值 | 理由 |
|---|---|---|
| key 粒度 | 座位 + 日期 | 锁粒度决定并发度。只锁座位会导致不同日期互相阻塞 |
| TTL | 10 秒 | 长了崩溃后锁死座位；短了业务没跑完就过期。**敢设短是因为有 L2 兜底** |
| 阻塞策略 | 非阻塞，抢不到直接 409 | 排队会占 Tomcat 线程 + 数据库连接，且等待收益极低 |

**选锁粒度的判据：锁的范围要刚好覆盖"会互相冲突的那批操作"。**

### 1.5 已知局限（要能主动说）

1. 锁过期但业务没跑完 → 工业方案是看门狗续期（Redisson），本项目选择不续期、靠 L2 兜底
2. Redis 主从切换丢锁 → RedLock 想解决但争议大，本项目不追求
3. 不可重入 → 本场景无嵌套加锁

**这三条不解决的底气都来自同一句：L1 只是性能层，正确性在 L2。**

## 2. L2：数据库行锁（互斥层）

### 2.1 为什么要这一层

Redis 锁有四种漏法：

1. 锁过期但业务没跑完（最常见）
2. 主从切换丢锁
3. Redis 重启没恢复
4. `unlock` 网络失败没送达

锁在缓存里，数据在数据库里。**锁丢了、数据还在，于是没人拦着第二个人写。**

数据库的锁和事务同生共死，事务不结束锁不放手 —— 这是"不会丢"的那一层。

### 2.2 FOR UPDATE 做了什么

```sql
SELECT id FROM lib_seat WHERE id = ? FOR UPDATE
```

两个效果：

1. **当前读**：绕过 MVCC，读最新已提交数据
2. **加排他锁（X 锁）**：持有到事务结束

### 2.3 为什么必须写在事务里

**锁的持有者是事务，不是方法、不是 SQL、不是连接。**

没有 `@Transactional`，MyBatis 自动提交，`FOR UPDATE` 加完立刻释放，等于没加。

```java
@Transactional(isolation = Isolation.READ_COMMITTED)
public BookingView create(...) {
    Long locked = seatMapper.lockForUpdate(seatId);   // 加锁
    ...                                               // 检测 + 插入
}                                                     // 提交，锁释放
```

> 坑：`@Transactional` 靠代理，**同类方法内部调用会失效**，事务静默不生效，锁也跟着失效。

### 2.4 为什么锁 `lib_seat` 而不是 `seat_booking`

要防的是「插入」，而**要插入的那一行还不存在，没有索引条目可以加锁**。

所以拿一个必然存在的行当锚点 —— 座位本身。用"锁父行"串行化"子记录的插入"。

判断法则：

- 防插入 → 锁父行
- 防更新已存在的行 → 直接锁那一行

### 2.5 锁多少行，由索引决定

InnoDB 的锁加在**索引条目**上，不是"行"这个抽象概念上。

| 查询 | 结果 |
|---|---|
| `WHERE id = 3`（主键） | 只锁 1 行 |
| `WHERE status = 1`（无索引） | 全表扫描，扫描到的行全被锁 ≈ 锁表 |

### 2.6 RC vs RR

| 缩写 | 全称 | 快照时机 | 特点 |
|---|---|---|---|
| RU | Read Uncommitted | — | 能读未提交，脏读 |
| **RC** | **Read Committed** | **每条 SELECT 重新拍** | 看得见别人刚提交的 |
| **RR** | **Repeatable Read** | **事务第一条 SELECT 拍，全程复用** | 事务内数据稳定，看不见后来者 |
| SERIAL | Serializable | — | 排队 |

MySQL InnoDB 默认 RR，Oracle/PG 默认 RC。

**本项目的两个理由：**

1. **锁范围**：RC 下间隙锁基本关闭（RR 下范围查询/非唯一索引会锁空隙），锁更小、并发更高
2. **可见性（关键）**：B 在事务开始时 `findById` 已确立 ReadView。若为 RR，A 提交后 B 的 `findFirstConflict` 仍用旧快照，**看不见 A 刚插入的那一行** → 判定"无冲突" → 重复预约。RC 每条语句重新拍快照，才能看见。

> **锁解决了"谁先谁后"，隔离级别决定了"后来者能不能看见前一个人的成果"。两者必须配套。**

### 2.7 代价

- `innodb_lock_wait_timeout` 默认 50 秒，超时抛 `Lock wait timeout exceeded`
- 阻塞期间数据库连接一直被占，高并发下会打穿连接池 → 这是必须要有 L1 的原因
- 单行锁不会死锁；多行不同顺序会（InnoDB 有死锁检测，回滚代价小的事务）
- 不挡读：普通 SELECT 是快照读，不加锁

## 3. L3：时间区间判据（语义层）

### 3.1 为什么要这一层

前两层只保证"同一座位的写不并发"，但**串行化不等于业务正确**：

- 座位 1 已有 08:00–10:00，要订 10:00–11:00 → 应该允许
- 座位 1 已有 08:00–10:00，要订 09:00–11:00 → 必须拒绝

锁看这两件事一样。**判断"什么算冲突"是第三层的事。**

### 3.2 判据推导

把预约看成左闭右开区间 `[start, end)`。

**正向枚举"重叠"会漏**（包含、被包含、左交、右交……），**反向枚举"不重叠"只有两种**：

```
candidate.end <= existing.start     （候选完全在前）
candidate.start >= existing.end     （候选完全在后）
```

德摩根取反，重叠条件：

```
existing.start < candidate.end   AND   existing.end > candidate.start
```

**用 `>` `<` 而非 `>=` `<=`**，因为区间左闭右开，18:00 结束与 18:00 开始不算冲突。

| 相对位置 | 判定 |
|---|---|
| 完全在前 | 不冲突 |
| 首尾相接（前） | **不冲突** |
| 左重叠 | 冲突 |
| 包含已有 | 冲突 |
| 首尾相接（后） | **不冲突** |
| 完全在后 | 不冲突 |

### 3.3 SQL

```sql
SELECT id, ... FROM seat_booking
WHERE seat_id = #{seatId}
  AND book_date = #{bookDate}
  AND status IN ('BOOKED', 'CHECKED_IN', 'LEAVING')
  AND start_time < #{endTime}
  AND end_time > #{startTime}
ORDER BY start_time
LIMIT 1
```

- `status IN (...)` 是**业务语义**：只有这三个状态算占用中，CANCELLED / EXPIRED / FINISHED 已释放
- `LIMIT 1`：只关心有没有，且能拿最早那条给用户做提示
- `ORDER BY start_time`：提示"该座位 09:00-10:00 已被预约"

### 3.4 第二个维度：同一个人不能撞时段

同一用户订两个**不同座位**的同一时段：

- Redis 锁不同（sear:1 vs seat:2）
- 行锁不同
- 座位冲突检测各自通过

三层全放行 → 一个人占两个座位。所以需要同一判据、换个维度再查一次：

```sql
SELECT COUNT(*) FROM seat_booking
WHERE user_id = #{userId} AND book_date = #{bookDate}
  AND status IN ('BOOKED', 'CHECKED_IN', 'LEAVING')
  AND start_time < #{endTime} AND end_time > #{startTime}
```

**判据一个字没变，只换了过滤维度的第一列。**

> **已知边界**：同一用户的两个请求真同时到达（不同座位），两边都查不到对方（都没提交），仍可能双开。修法：加 `lock:user:{userId}:{date}` 一把用户维度的锁，单用户并发极低，几乎无成本。

### 3.5 为什么每日额度查两次

锁外一次是**乐观预判**（快速失败，不浪费锁），锁内一次才是**权威判定**。

因为锁外检查和真正插入之间隔着抢锁、等行锁，可能几百毫秒，期间额度可能已被另一个请求用掉。

> **凡是 check-then-act，真正的检查必须发生在临界区之内。**

### 3.6 索引

```sql
KEY idx_seat_date (seat_id, book_date, status, start_time)
```

最左前缀：`seat_id = ?` → `book_date = ?` → `status IN (...)` → `start_time < ?` 都用得上；`end_time > ?` 用不上，回表过滤。

**规律：等值列在前，范围列在后。某列用了范围条件，它后面的列就用不上索引。**

用户维度走 `idx_user_date (user_id, book_date)`。

### 3.7 同一判据的第三处：筛空闲座位

```sql
AND NOT EXISTS (
  SELECT 1 FROM seat_booking b
  WHERE b.seat_id = s.id AND b.book_date = #{bookDate}
    AND b.status IN ('BOOKED', 'CHECKED_IN', 'LEAVING')
    AND b.start_time < #{endTime} AND b.end_time > #{startTime}
)
```

一次查询筛完整个阅览室，避免"查所有座位再逐个查冲突"的 N+1。

## 4. 三层协同

| 层 | 职责 | 保证 | 失效后果 |
|---|---|---|---|
| L1 Redis 锁 | 把并发挡在数据库外 | 性能（可失效） | 只是变慢 |
| L2 行锁 | 同座位写串行化 | 互斥（不会丢） | 高并发下超卖 |
| L3 区间检测 | 定义什么算冲突 | 语义（业务正确） | 串行地插入两条重叠记录 |

**空窗期接力**：`finally { unlock }` 执行在事务提交之前，Redis 锁已放、数据未落。此时 B 抢到锁，但会卡在 L2 的行锁上，等 A 提交后才继续 —— 而且必须靠 RC 才能看见 A 刚插入的行。

---

## 5. 已知边界

1. **同用户跨座位并发**：需额外加用户维度锁
2. **不支持跨天预约**：`book_date + start_time + end_time` 隐含同天假设，跨天需改 `DATETIME`
3. **时间不带时区**：`LocalTime` 无时区，单机房可用
4. **无法用唯一索引硬顶**：区间重叠不能用唯一索引表达（MySQL 无排他约束），除非拆 30 分钟 slot 子表

---

## 6. 设计要点速览

> 用 Redis 的 `SET key token NX PX` 做非阻塞分布式锁，key 按「座位 + 日期」定粒度，令牌用 UUID 保证只删自己的锁，释放走 Lua 保证"比较再删除"的原子性。这层只做流量收敛，不承担正确性。
>
> 正确性由数据库行锁兜底：事务内对 `lib_seat` 主键行 `FOR UPDATE`，锁父行是因为要保护的预约记录还不存在、无法直接加锁。隔离级别显式设为 RC，保证后续冲突检测能看见别人刚提交的插入。
>
> 业务语义由区间判据定义：用左闭右开区间的 `start < :end AND end > :start` 判断重叠，同一判据复用于座位冲突、用户撞时段、空闲座位筛选三处。
>
> 三层解耦的价值是：性能层可以随便降级，正确性不会跟着塌。
